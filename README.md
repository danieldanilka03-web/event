# События — управление мероприятиями и бронирование билетов

Курсовая работа (MVP): веб-приложение для публикации мероприятий, записи участников
и выдачи электронных билетов с QR-кодом. Три роли: участник, организатор, администратор.
Для мероприятий с фиксированной рассадкой работает интерактивная схема зала на SVG:
участник выбирает ряд и место кликом, место бронируется на 10 минут.

## Стек

| Назначение | Выбор |
| --- | --- |
| Фреймворк | Next.js 15 (App Router, Server Actions, Route Handlers) |
| Язык | TypeScript (strict, без `any`) |
| БД | PostgreSQL (Neon) + Drizzle ORM |
| Авторизация | JWT (HS256, `jose`) в httpOnly-cookie, `bcryptjs` для паролей |
| Валидация | Zod — на сервере, во всех Server Actions и Route Handlers |
| Стили | Tailwind CSS 4, собственные shadcn-подобные компоненты |
| Иконки | lucide-react |
| Схема зала | SVG-компонент с кликабельными креслами |
| QR | `qrcode` (dataURL, генерация на сервере) |
| Даты | `Intl.DateTimeFormat` с явным `timeZone: 'Europe/Moscow'` |

Интерфейс на русском, даты в формате `дд.мм.гггг, чч:мм`, часовой пояс отображения
`Europe/Moscow`. В базе время хранится в UTC (`timestamptz`).

Форматирование дат идёт через `Intl` с **явным** `timeZone: 'Europe/Moscow'`, а не через
таймзону процесса. Это принципиально: серверные компоненты на Vercel работают в UTC, а
клиентские — в зоне пользователя. Без явной зоны одна и та же запись показывала бы
«12:00» в каталоге и «15:00» в личном кабинете. По той же причине `datetime-local`
в форме переводится в UTC функциями `toLocalInputValue` / `fromLocalInputValue`.

## Роли и права

- **Участник** — смотрит каталог, записывается на мероприятия, отменяет записи,
  видит электронные билеты. Роль `participant` присваивается при самостоятельной регистрации.
- **Организатор** — всё участника плюс CRUD своих мероприятий, перевод `draft → published`,
  отмена мероприятия, список участников, метрики. Чужие события недоступны.
- **Администратор** — всё вышеперечисленное для любых мероприятий плюс управление
  пользователями (роль, блокировка) и статистика платформы.

Правила доступа применяются дважды: в `src/middleware.ts` (быстрая проверка маршрута)
и в `requireRole(...)` внутри каждого Server Action и Route Handler. На каждом защищённом
запросе роль и флаг `is_blocked` перечитываются из БД, поэтому блокировка действует
немедленно, без ожидания истечения токена.

## Фиксированная рассадка: схема зала и временная бронь

Часть мероприятий создаётся с залом. Организатор включает флажок «Фиксированная рассадка»
в форме создания — приложение подбирает раскладку (ряды по 10 кресел, буквенные ряды A, B, C…)
и создаёт ровно `max_seats` кресел в таблице `seats`. Изменить раскладку после создания нельзя:
места уже заняты или забронированы.

Как выглядит участие:

1. Участник кликает по свободному креслу в SVG-схеме.
2. Сервер создаёт **временную бронь на 10 минут** (`seat_holds.expires_at`) и блокирует кресло
   для всех: у другого участника оно становится «В брони» и не кликается.
3. В интерфейсе появляется таймер обратного отсчёта; кнопки «Отпустить» и «Подтвердить».
4. «Подтвердить» создаёт регистрацию с выбранным местом и снимает бронь.
5. Если за 10 минут ничего не подтвердить, место возвращается в свободные. Отдельная задача
   для этого не нужна: истёкшие брони удаляются лениво при каждом обращении к схеме зала.

### Почему место нельзя «украсть»

Бронирование выполняется в одной транзакции: строка кресла блокируется
`SELECT … FOR UPDATE OF s`, поэтому два одновременных клика по одному креслу выстраиваются
в очередь. Истёкшая бронь удаляется **только по условию `expires_at <= now()`** —
безусловный `DELETE` сносил бы чужую живую бронь, и второй участник забрал бы занятое место.
Дополнительно работает `UNIQUE (seat_id)`: у кресла не может быть двух незавершённых броней.
У одного пользователя на мероприятие держится только одна бронь — выбрал другое кресло,
предыдущее освобождается.

### Данные

```sql
seats(id, event_id, row_label, number, category)   -- UNIQUE(event_id, row_label, number)
seat_holds(id, seat_id, event_id, user_id, expires_at)  -- UNIQUE(seat_id) + индекс по expires_at
registrations.seat_id                                -- выбранное кресло, NULL без рассадки
events.layout_rows, events.seats_per_row             -- NULL = фиксированной рассадки нет
`

## Лист ожидания (Waitlist) и алгоритмическое перераспределение мест

Когда на популярное мероприятие заканчиваются места (`occupied_seats >= max_seats`), включается подсистема **Листа ожидания** (очередь с приоритетами и TTL-офферами). Это ключевая нетривиальная операция для диплома, выходящая далеко за рамки обычного CRUD.

### Как работает алгоритм перераспределения

1. **Вход в очередь:** Участник нажимает «Встать в лист ожидания» (`joinWaitlistAction`). Запись создаётся со статусом `'waiting'` и приоритетом по умолчанию (0).
2. **Алгоритм распределения (Queue Dispatcher):**
   При отмене билета зарегистрированным участником транзакция не просто уменьшает счётчик, а атомарно вызывает `dispatchWaitlistOfferWithClient`:
   - Блокирует очередь `SELECT ... FOR UPDATE` с сортировкой `ORDER BY priority ASC, created_at ASC LIMIT 1`.
   - Если кандидат найден: статус меняется на `'offered'`, бронируется место (в зале ставится `seat_holds`) и устанавливается тайм-аут на 30 минут (`expires_at = now() + 30 min`). Общий счётчик мест не уменьшается, защищая слот от перехвата сторонними пользователями.
   - Если очередь пуста: место возвращается в общий доступ (`occupied_seats = occupied_seats - 1`).
3. **Оффер участнику:**
   - Кандидат видит баннер с тикающим таймером в личном кабинете «Мои билеты» и на странице события.
   - Кандидат может «Подтвердить и забрать билет» (`claimWaitlistSpotAction`) либо «Отказаться» (`rejectWaitlistSpotAction`).
   - При отказе или истечении 30 минут (`cleanExpiredOffers`) место **каскадно передаётся следующему** кандидату в очереди.
4. **Панель управления организатора (`/organizer/events/[id]/waitlist`):**
   - **Метрики очереди:** сколько ожидают, предложено сейчас, выкуплено, конверсия листа ожидания.
   - **Ручное продвижение очереди:** организатор может запустить раунд распределения (`manualDispatchWaitlistAction`).
   - **Управление приоритетами:** изменение приоритета кандидата (VIP `-1`, Обычный `0`, Сниженный `+1`), влияющее на позицию в очереди FIFO+Priority.
   - **Исключение из очереди:** безопасное снятие кандидата организатором.``

## Как устроена регистрация на мероприятие

Критичный сценарий (`src/server/actions/registrations.ts`) выполняется в одной транзакции:

1. Проверяем, что событие `published` и ещё не началось; строка события блокируется
   через `SELECT … FOR UPDATE`.
2. Отсекаем повторную запись: если активная регистрация уже есть — откат и
   «Вы уже зарегистрированы».
3. Атомарно занимаем место:
   ```sql
   UPDATE events SET occupied_seats = occupied_seats + 1
   WHERE id = $1 AND status = 'published' AND occupied_seats < max_seats
   RETURNING id
   ```
   Ноль строк — «Свободных мест нет», транзакция откатывается.
4. Если у мероприятия есть зал: кресло должно принадлежать мероприятию, быть свободным и
   быть забронировано именно этим пользователем. Иначе — «Бронь истекла или место занято».
5. Вставляем регистрацию либо, если запись была отменена, переводим её в `active`
   (новую строку вставить нельзя из-за `UNIQUE (event_id, user_id)`). Бронь снимается.
5. Коммит и редирект на `/tickets/[id]`.

Отмена симметрична: `status = 'cancelled'` и `occupied_seats = occupied_seats - 1`
в той же транзакции; повторная отмена и отмена прошедшего события ничего не меняют.

Дополнительно БД страхует логику: `CHECK (occupied_seats <= max_seats)` и
`UNIQUE (event_id, user_id)`.

## REST API

Все операции чтения, добавления, изменения и удаления доступны по HTTP. Формат ответа
единый: `{ ok: true, data }` или `{ ok: false, error, fieldErrors? }`. Коды: `201` при
создании, `400` при ошибке входных данных, `401` без входа, `403` при недостатке прав,
`404` если объект не найден, `409` при конфликте (занятое место, повторная регистрация).

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| `POST` | `/api/auth/login` | все | вход, ставит httpOnly-cookie с JWT |
| `POST` | `/api/auth/logout` | все | выход, удаляет cookie |
| `GET` | `/api/events` | все | публичный каталог, `?q=&category=&from=&to=&page=` |
| `POST` | `/api/events` | организатор, админ | создать мероприятие (`fixedSeating: true` — с залом) |
| `GET` | `/api/events/{id}` | все | мероприятие со схемой зала |
| `PATCH` | `/api/events/{id}` | владелец, админ | изменить; `{"status": "published"}` меняет статус |
| `DELETE` | `/api/events/{id}` | владелец, админ | удалить |
| `GET` | `/api/events/{id}/seats` | авторизованные | схема зала со статусами кресел и своей бронью |
| `POST` | `/api/events/{id}/seats` | авторизованные | забронировать кресло на 10 минут |
| `DELETE` | `/api/events/{id}/seats` | авторизованные | снять свою бронь |
| `GET` | `/api/registrations` | авторизованные | мои регистрации с местами |
| `POST` | `/api/registrations` | авторизованные | зарегистрироваться (`eventId`, `seatId`) |
| `DELETE` | `/api/registrations?registrationId=` | авторизованные | отменить регистрацию |

Пример:

```bash
curl -X POST http://localhost:3000/api/events/ID/seats \
  -H 'content-type: application/json' -b cookies.txt \
  -d '{"seatId":"UUID-кресла"}'
# {"ok":true,"data":{"seatId":"...","expiresAt":"2026-10-13T11:46:07.031Z"}}
```

Интерфейс при этом ходит через Server Actions — они вызывают те же функции слоя данных,
поэтому REST и UI не расходятся в логике.

## Безопасность

- Пароли хранятся только как bcrypt-хеш (cost 10) и никогда не отдаются на клиент.
- JWT-секрет только в переменных окружения; в payload — лишь `sub` и `role`.
- Все SQL-запросы параметризованы; `ILIKE`-шаблоны экранируются.
- React экранирует вывод по умолчанию, `dangerouslySetInnerHTML` не используется
  (QR отдаётся как dataURL).
- Администратор не может понизить или заблокировать самого себя, и система не может
  остаться без администраторов.

## Развёртывание на Vercel + Neon

Короткий порядок (подробности — в следующем разделе):

1. Создать проект в Neon, скопировать **pooled** строку подключения.
2. Выполнить миграции и сид локально: `npm run db:migrate && npm run db:seed`.
3. Залить код в Git-репозиторий и импортировать его в Vercel.
4. Задать `DATABASE_URL` и `JWT_SECRET` в переменных окружения Vercel.
5. Задеплоить, затем выставить `NEXT_PUBLIC_APP_URL` равным боевому домену
   и **передеплоить** — переменные с префиксом `NEXT_PUBLIC_` встраиваются на этапе сборки.

git init
git add .
git commit -m "Курсовая работа: управление мероприятиями и бронирование билетов"
git branch -M main
git remote add origin https://github.com/<твой-логин>/<название-репозитория>.git
git push -u origin main
```

Перед `git add` убедись, что `.env.local` не попадает в коммит:

```bash
git status --short   # .env.local быть не должно
```

`.gitignore` уже содержит `.env.local`, `node_modules` и `.next`, так что
случайно они не уедут в репозиторий.

### Шаг 4. Создать миграции и данные в Neon

Секреты для QR и сессий — сгенерировать локально:

```bash
openssl rand -base64 48
```

Создать файл `.env.local`:

```bash
cp .env.example .env.local
```

Вписать в него:

- `DATABASE_URL` — pooled строка из Neon (шаг 2);
- `JWT_SECRET` — результат `openssl rand -base64 48`;
- `NEXT_PUBLIC_APP_URL` — пока `http://localhost:3000`.

Затем:

```bash
npm install
npm run db:migrate   # создаст таблицы
npm run db:seed      # 8 пользователей и 15 мероприятий
npm run dev          # проверить локально на http://localhost:3000
```

`db:seed` можно пропустить, если нужны пустая база.

### Шаг 5. Задеплоить на Vercel

1. Импортировать репозиторий: Vercel → **Add New → Project** → выбрать
   репозиторий из GitHub. Рамка Next.js определится сама, настройки менять
   не нужно.
2. В **Environment Variables** добавить:

   | Key | Value |
   | --- | --- |
   | `DATABASE_URL` | pooled строка Neon |
   | `JWT_SECRET` | тот же секрет, что локально |

3. Нажать **Deploy** и дождаться сборки.

### Шаг 6. Задать боевой домен и передеплоить

После первого деплоя Vercel выдаст адрес вида `https://event-tickets-abc.vercel.app`.
В Environment Variables добавить:

| Key | Value |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | `https://event-tickets-abc.vercel.app` |

И **передеплоить** (Deployments → redeploy). Переменные `NEXT_PUBLIC_*`
подставляются в бандл на этапе сборки, поэтому без передеплоя QR-код
останется со старым адресом.

### Шаг 7. Проверить, что всё работает

Зайти на боевой домен и пройти по ролям (пароль у всех `Password123!`):

- `admin@example.com` — `/admin`: статистика, пользователи, модерация;
- `organizer1@example.com` — `/organizer`: создать мероприятие, опубликовать;
- `participant1@example.com` — записаться на мероприятие, открыть `/my-tickets`,
  показать QR-код.

Если что-то не открывается:

| Симптом | Причина |
| --- | --- |
| «DATABASE_URL не задан» | не задана переменная окружения на Vercel |
| «Ваше соединение прервано» / timeout | в Neon взят direct connection вместо pooled |
| Таблиц нет | не выполнен `npm run db:migrate` |
| Не пускает в `/admin` | залогинен не администратором |
| QR ведёт не туда | не задан `NEXT_PUBLIC_APP_URL` или нет передеплоя |

### Локально без Neon

Если Neon под рукой нет, приложение работает и с обычным PostgreSQL —
драйвер выбирается по строке подключения автоматически:

```bash
createdb eventdb
# в .env.local:
# DATABASE_URL=postgresql://localhost:5432/eventdb
npm run db:migrate && npm run db:seed && npm run dev
```
